## Review Focus

1. **Tampered direct Server Action payloads bypassing hidden UI controls:** A `MEMBER` or removed member can invoke Server Actions (`createTaskAction`, `updateTaskAction`, `deleteProjectAction`, `addMemberAction`) with valid UUIDs from Team B or forbidden fields; tests must prove server-side rejection even when UI controls are absent.
2. **Active-team navigation context (`lastActiveTeamId`) vs. authorization:** Switching `lastActiveTeamId` to Team A or tampering with a URL `/teams/<TeamB>/...` must never grant read/write access to Team B, and removing a member must fire `trg_clean_last_active_team` / `removeMemberAction` cleanup immediately.
3. **Deleted/anonymized user with lingering session cookie:** Calling `deleteAccountAction` (or setting `user.deletedAt`) must immediately block all protected pages (`requireAuthPage` -> `/sign-in`) and Server Actions (`getActionUser` -> `null`), even if an older browser cookie is replayed.
4. **Notification & ActivityLog privacy after revocation or soft-delete:** Revoking Team B membership or soft-deleting a project/task must immediately scrub titles, actors, avatars, and `href` (`isAccessible: false`, `href: null`) in `getNotificationsAction`, and hide `project_deleted` / soft-deleted project activity while retaining `task_deleted` (when project active) and `comment_deleted` (when task & project active) without exposing comment text or emails.
5. **Real PostgreSQL trigger & concurrency invariants:** Concurrent `transferOwnershipAction` / `removeMemberAction` / `updateTaskAction` / `deleteAccountAction` requests must serialize cleanly via `FOR NO KEY UPDATE` / `FOR UPDATE` without deadlocking or violating `idx_team_single_owner`, `verify_team_owner_invariant`, `chk_project_dates`, or `task_teamId_assignedToId_fkey`.

### Why Run Playwright Against `next build && next start` in CI (with `next dev` Option Locally)?
Because `next.config.ts` enables `cacheComponents: true` and `partialPrefetching: true`, running Playwright against a production build (`npx next build && npx next start -p 3005 -H 127.0.0.1`) verifies the exact compiled RSC/Server Action caching and `proxy.ts` behavior that ships to production, while keeping `NODE_ENV=production` **safe** via `EMAIL_PROVIDER` / test-mode handling — wait: check `src/lib/email.ts`!
- **Important finding from `src/lib/email.ts`:** In `NODE_ENV === "production"`, `sendEmail()` throws unless `EMAIL_PROVIDER` is configured (and rejects `"stub"`). `src/lib/auth.ts` has `requireEmailVerification: false` and `sendOnSignUp: false`, so sign-up and sign-in do **not** call `sendEmail()`, whereas forgot-password / resend-verification *do* call `sendEmail()`.
- **Decision for test server mode:** Running Playwright with `next dev -p 3005 -H 127.0.0.1` (`NODE_ENV=development` or `test`) avoids `sendEmail()` throwing on password-reset flows without touching `src/lib/email.ts`! Conversely, running `next build && next start` verifies production compilation, but password-reset `sendEmail()` would throw unless `src/lib/email.ts` supports a test sink. Since **zero application code changes** is cleanest and `requireEmailVerification: false`, we recommend **`next dev --webpack` or `next dev -p 3005` for local/E2E runs including password-reset flows**, OR running `next build && next start` in CI while testing password-reset email token verification at the Vitest integration layer (`NODE_ENV=test`) where `sendEmail()` stubs cleanly. We will document both explicitly in `playwright.config.ts` (`PLAYWRIGHT_SERVER_MODE=start|dev`, defaulting to `dev` locally or `start` when `CI=true` with forgot-password UI toast/submission tested cleanly or skipped if `NODE_ENV=production` blocks stub). Better yet: let's ask the user whether a tiny test-only email sink / `ALLOW_TEST_EMAIL_STUB` or running Playwright on `next dev` vs `next start` is preferred (see Section 8).

## 4. Test Data, Fixtures & Authentication Strategy

### Deterministic Multi-Tenant Test World (`seedTestWorld`)
Every integration and E2E suite seeds a reproducible, deterministic fixture graph with fixed UUIDs and known credentials:
- **Users (all verified/credential accounts created via Better Auth password hashing or `auth.api.signUpEmail`):**
  - `ownerA` (`owner-a@test.local`) — `OWNER` of **Team Alpha**, `lastActiveTeamId = teamAlpha.id`
  - `managerA` (`manager-a@test.local`) — `MANAGER` of **Team Alpha**
  - `memberA` (`member-a@test.local`) — `MEMBER` of **Team Alpha**
  - `memberA2` (`member-a2@test.local`) — second `MEMBER` of **Team Alpha** (for reassignment, comment-author isolation, multi-recipient notifications)
  - `ownerB` (`owner-b@test.local`) — `OWNER` of **Team Beta** (strict outsider to Team Alpha)
  - `multiUser` (`multi@test.local`) — `MEMBER` of **Team Alpha** AND `OWNER` of **Team Beta** (tests `lastActiveTeamId` switching and cross-team notification aggregation/sanitization)
  - `unaffiliated` (`solo@test.local`) — active user with zero teams (tests onboarding & zero-team boundaries)
- **Teams:** `teamAlpha` (owned by `ownerA`), `teamBeta` (owned by `ownerB` or `multiUser`).
- **Projects & Tasks:** Active `projectAlpha1` (`ACTIVE`), `projectAlpha2` (`PLANNING`), `projectBeta1` (`ACTIVE`), plus helper factories for `createTestTask`, `createTestComment`, `createTestProject` with deterministic UTC dates relative to `new Date()` for `overdue` / `today` / `this_week` filters and pagination batches (`30` tasks for `25/page` verification).

### Authentication & Multi-User Session Strategy
1. **Vitest Real-DB Integration (`tests/integration/helpers/auth-context.ts`):**
   - Calls `auth.api.signUpEmail` / `auth.api.signInEmail` (via `asResponse: true`) against the real Better Auth instance backed by `aipm_test`, extracting the real `Set-Cookie` (`better-auth.session_token=...`) header.
   - Uses an `AsyncLocalStorage<Headers>` shim for `vi.mock("next/headers", ...)` so each test can run `await asUser(sessionCookie, () => createTaskAction(...))` and switch actors (`ownerA` -> `managerA` -> `memberA` -> `ownerB` -> unauthenticated) within the same test without mocking `getActionUser` or `auth.api.getSession`!
   - `next/cache` (`revalidatePath`) is a no-op spy; `next/navigation` (`redirect`, `notFound`) throws typed sentinel errors (`NextRedirectError`, `NextNotFoundError`) so server loaders (`requireAuthPage`, `requireTeamMember`) can also be asserted directly against PostgreSQL.
2. **Playwright Browser E2E (`tests/e2e/helpers/auth.ts`):**
   - Signs in via real browser UI (`/sign-in`) or real `POST /api/auth/sign-in/email` inside `browser.newContext()`, storing `Set-Cookie` in each role's isolated `BrowserContext` (`ownerContext`, `managerContext`, `memberContext`, `outsiderContext`).
   - Supports simultaneous open tabs across roles (e.g., `managerContext` reassigns a task or completes a project while `memberContext` receives the updated notification bell count and navigates cross-team).

## 8. Risks, Limitations & Open Decisions

### Technical Risks & Limitations
1. **Local PostgreSQL Absence:** No local Postgres or Docker is installed yet; Milestone 4.1 execution depends on provisioning Option A (`winget` Postgres 16/17) or Option B (Docker/WSL2 Postgres).
2. **`src/lib/email.ts` in `NODE_ENV=production` (`next start`):** `sendEmail()` throws when `NODE_ENV=production` and `EMAIL_PROVIDER` is unset/stub. Sign-up and sign-in (`requireEmailVerification: false`) are unaffected, but browser E2E tests triggering password-reset email sending will fail under `next start` unless run against `next dev` or with a test-only email capture mechanism.
3. **Google OAuth:** Real Google OAuth (`REQ-AUTH-02`) requires external Google network callbacks and credentials, so OAuth callback handshake remains out of live E2E scope (only button presence / conditional config is tested).
4. **Next.js 16 `cacheComponents: true`:** `next start` caches differently from `next dev`; running Playwright against `next build && next start` in CI catches stale `revalidatePath` bugs that `next dev` may mask.
5. **Sequential DB Tests:** `TRUNCATE ... CASCADE` requires `fileParallelism: false` and `workers: 1`, keeping integration/E2E runs deterministic at the cost of ~1–3 minutes total CI runtime.

### Decisions Requiring User Approval Before Implementation
1. **Test PostgreSQL Provisioning Choice:** Approve **Option A (Native Windows PostgreSQL 16/17 via `winget`)**, **Option B (Docker Desktop / WSL2 Postgres container)**, or **Option C (Isolated Neon test branch)**.
2. **Playwright Target Server Mode:** Approve running Playwright E2E against `next build && next start` by default (best production fidelity for Next.js 16 `cacheComponents: true`, keeping forgot-password email delivery tested in Vitest `NODE_ENV=test`), or `next dev` (supports stubbed password-reset emails in browser without touching `src/lib/email.ts`).
